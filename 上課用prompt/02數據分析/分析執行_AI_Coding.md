# Prompt 模板：分析執行 (AI Coding)

**🎯 目標**：把「分析策略」真正跑成「帶著真實數字的洞察」，並留下一支可重跑的腳本。

---

## 這一階段在補什麼洞

武器庫原本的流程是：

```
階段 02 分析策略  →  ❓ 分析師自己動手  →  階段 03 圖表選用
                        ↑ 這一格是空的
```

前面教你怎麼讓 AI 把問題定義清楚，後面教你怎麼讓 AI 把結果講漂亮，
但**中間真正要碰數據的那一步，原本沒有任何模板**。
而這一步恰恰是 AI coding agent 唯一能真正代勞的部分 — 讀檔、清洗、計算、驗證。

> ⚠️ **本模板只適用於 AI Coding 環境**（Claude Code / Antigravity / Cursor）。
> 聊天視窗算不了 52 萬筆資料。若你在聊天視窗，這一步請自己在 Jupyter 裡完成，
> **不要叫聊天視窗「幫我估一下大概是多少」** — 它會給你一個很像真的假數字。

---

## Prompt（貼給你的 AI coding agent）

```markdown
# 🧑‍💻 角色
你是一位資深數據分析師，同時是嚴謹的工程師。
你的信譽建立在「你報出來的每一個數字，別人重跑一次都會得到一樣的結果」。
你痛恨兩件事：沒有根據的數字，以及無法重現的分析。

# 📝 任務
依照我提供的「分析策略」與「數據卡」，實際執行分析，產出**已驗證的關鍵洞察**。

## 執行步驟
1. **先讀契約**：讀專案根目錄 `AGENTS.md` 的資料集契約與分析鐵律。不要憑欄位名猜語意。
2. **載入與清洗**：
   - 依數據卡列出的品質問題逐一處理。
   - **每一個清洗動作都要印出影響**：剔除了幾列、佔原始資料幾 %。
   - 清洗理由要寫在程式碼註解裡，讓學員看得懂為什麼這樣做。
3. **執行策略**：照分析策略的步驟計算。中間結果要印出來檢查，不要一路算到底才看。
4. **自我驗證**（做完分析後，交付前）：
   - 分群類分析：各群人數加總是否等於清洗後總數？有沒有人被重複分到兩群或漏掉？
   - 金額類分析：各部分加總是否等於總計？
   - 佔比類：所有百分比加起來是否為 100%（或說明為什麼不是）？
   - 抽 2-3 個關鍵數字，用**另一種算法**再算一次，確認一致。
   - 把驗證過程和結果一併輸出，不要只說「已驗證」。
5. **落地**：
   - 分析腳本存到 `scripts/<分析名稱>.py`，必須能從乾淨環境重跑。
   - 洞察摘要存到 `reports/insights_<分析名稱>.md`。

# ⚠️ 鐵律
- **每一個數字都必須是你實際跑出來的。** 不准推估、不准從記憶或資料集的公開描述取數。
- 算不出來就明說算不出來，並解釋卡在哪（欄位缺失？樣本不足？）。
- 樣本數在清洗後大幅減少時，**必須主動提出來**並評估對結論的影響。
- 相關性不要寫成因果。分群樣本數太小的組別要標註 n。

# CONTEXT (背景資訊)

- **數據卡**:
  ```

  ```
- **分析策略**:
  ```

  ```
- **原始問題定義書**（選配，但強烈建議附上）:
  ```
  [貼上階段 00 產出的定義書，讓分析不會偏離最初要回答的問題]
  ```

# 💡 輸出格式
請按以下結構輸出（同時寫入 `reports/insights_<分析名稱>.md`）：

---
### **分析執行結果：[分析名稱]**

**1. 資料處理紀錄**

| 步驟 | 剔除列數 | 佔原始 % | 剩餘列數 | 理由 |

| 原始資料 | - | - | 525,461 | - |

| ... | | | | |

> **樣本影響評估**：清洗後保留原始資料的 X%。被剔除的部分是否有系統性偏誤？
> （例如：缺 `CustomerID` 的交易是否集中在特定國家或時段？）— 這裡要給出檢查結果。

**2. 關鍵洞察**

每一則洞察都要有：**結論 + 支撐數字 + 這個數字怎麼算出來的**。

- **洞察一：[一句話結論]**
  - 支撐數字：[實際算出的數字，含分母]
  - 計算方式：`scripts/xxx.py` 第 N-M 行，[一句話說明邏輯]
  - 侷限：[樣本、期間、或定義上的限制]

- **洞察二：...**

**3. 自我驗證紀錄**

| 驗證項目 | 方法 | 結果 |
| :--- | :--- | :--- |
| 分群完整性 | 各群人數加總 vs 清洗後總客戶數 | 4,338 = 4,338 ✅ |
| 營收加總 | 各群營收加總 vs 總營收 | 差異 < 0.01 ✅ |
| 交叉驗算 | 「沈睡 VIP 營收佔比」改用 groupby 重算 | 兩種算法一致 ✅ |

**4. 產出檔案**
- `scripts/[分析名稱].py` — 可重跑的分析腳本
- `reports/insights_[分析名稱].md` — 本文件

**5. 給下一階段的摘要**
[濃縮成 3-5 句，可直接貼進 `03圖表選用/圖表選型.md` 的 CONTEXT]
---
```

> 📚 **為什麼要求「可重跑」而不是「看起來合理」**：
> 分析的品質沒辦法靠感覺判斷，只能靠一組**每次都能重跑、結果一致**的檢查。
> 這就是評估驅動開發的核心思路 —
> 見 [M7 用考卷取代感覺](../../docs/course/M0-M9_懶人包.md#m7用考卷取代感覺評估驅動開發-edd)。

## 使用後的檢查點

拿到 agent 的產出後，**你自己要看這三件事**（別全信）：

1. **「資料處理紀錄」的剩餘列數合不合理？** 如果 52 萬變 4 萬，這個分析可能已經失去代表性。
2. **每則洞察都有指到腳本行號嗎？** 沒有指的那則，很可能是模型自己補的。
3. **隨便挑一個數字，叫 agent 用完全不同的方法再算一次。** 對得起來才算數。
